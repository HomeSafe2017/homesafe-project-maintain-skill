# 项目初始化、默认规范与模块设计

> 仅在首次初始化、修复笔记结构或进行模块规划时阅读。日常维护不加载本文件。

## 1. 初始化流程

1. 与用户确认本项目启用 Skill，并按主 SKILL 写入项目级记忆；
2. 阅读 [templates.md](templates.md)，在项目根目录创建 `AI_proj_note/`；
3. 创建九个常驻文件：`index.md`、`rule.md`、`files.md`、`blocks.md`、`vision_prefer.md`、`preview.md`、`note.md`、`progress.md`、`lessons.md`；`GitHistory.md` 在首次记录历史或归档决策时创建；
4. 保留全部 Section ID 与锚点。暂无内容时写标题和锚点占位，不编造项目事实；
5. 阅读项目目录、根 README、依赖清单和关键入口，建立最小可用认知；
6. 将下文默认规范写入 `RULES`，用户另有要求时以用户为准；
7. 检查字典路径、锚点唯一性、唯一键和 CURRENT 初始状态；
8. 检查 `.gitignore` 与待提交文件，防止密钥、环境文件、缓存和项目产出进入 Git。

已有项目只记录现状与偏差，不因初始化强制重构。

## 2. 初始化后的目录

```text
AI_proj_note/
├── index.md          # 项目字典：Section 路由、锚点、写入方式、唯一键
├── rule.md           # 当前有效规范、否决、修改要求、运维约束；无 Git 历史
├── files.md          # 文件级 FRAS 地图与可复用资产
├── blocks.md         # 模块职责、依赖、涉及文件、文件产物与清理级别
├── vision_prefer.md  # 产品 UI、视觉 token、组件样式、用户偏好
├── preview.md        # 模型的产品分析，明确区分事实与推断
├── note.md           # 未来意向与预留接口
├── progress.md       # CURRENT 单例状态与任务日志
├── lessons.md        # 踩坑与可复现解法
└── GitHistory.md     # 按需创建：里程碑、决策归档、功能提交历史
```

## 3. 写入 RULES 的默认开发规范

为每条分配稳定 `RULE-xxx`，记录日期和来源。以下规范是默认起点，不是让模型在日常维护中重复抄写的模板。

1. **注释规范**：代码每个部分写清功能注释，注释包含可全局搜索定位的 keyword，如函数名、模块名或业务术语；
2. **开发前模块规划**：动手前先明确模块划分、各自功能、输入输出和测试方式，规划写入 `BLOCKS`；切割遵循本文件第 4 节；
3. **Git 纪律**：有实质开发变更时每轮按项目约定提交；功能提交与 `notesync:` 笔记同步提交分离，历史以 commit hash 幂等记录，无实质变更不创建空提交；
4. **Git 安全纪律**：每次提交前确保 `.gitignore` 覆盖可能含密钥的配置、`.env` 等环境文件、项目产出、缓存和临时文件；只提交核心代码与必要文档。逐个检查 `git status` 和实际 diff，拿不准时先问用户；
5. **模块 README**：每个模块必须有 README，记录职责、输入输出、依赖、约定、文件产物与清理级别，并提供使用示例代码；
6. **可部署性**：根目录必须有 `requirements.txt` 或对应生态的等价依赖清单；根 README 必须列出无法仅凭依赖清单一键安装的系统工具、字体、数据库、模型或服务，并给出安装指引；
7. **复用优先**：设计前先判断组件未来是否可能复用，并检查 `REUSE`、`UI_REUSE`；仅改变参数或简单改动即可实现的相似功能必须参数化复用，禁止复制粘贴。新产生的复用资产登记回对应 Section；
8. **文件产物与清理标注**：每个文件和模块标注可能使用、产生的文件类型与地址，并区分“可能被自动清理”“允许清理”“重点保存”。标注写入模块 README 与 `BLOCKS`；可清理地址与正式数据在文件系统层面分目录；
9. **服务器运维配套记录**：nginx 配置、tmux 会话与操作、sh 启动/部署脚本等配套文件，记录位置、用途、变化原因和排查结论，写入 `OPS`；
10. **认知维护纪律**：`rule.md` 只保留当前有效内容，不写 Git 历史；所有笔记通过 `index.md` 定位并按唯一键局部写入，不整文重写、不重复记录。

## 4. 模块切割方法论

**检验标准**：不了解项目代码的人，仅凭目录结构、模块名和 README，就能大致说出每个部分做什么。做不到就是切割失败。

1. **按功能域切顶层模块，名字即功能**，不按 utils、common 等技术层次切顶层；
2. **相似功能和场景聚成一个包**：子模块共享父模块公共设施，各自保留入口、配置、说明和依赖声明，可独立理解和运行；
3. **共用与特殊分离**：会被两个以上子模块使用的逻辑上提到公共层，子模块只保留特殊逻辑；
4. **通用基础设施单独成模块**：服务宿主、输出产物等被多个业务模块依赖的能力，与业务模块平级，被引用而非各自实现；
5. **数据目录显式分离**：缓存、日志、上传、正式数据分目录，直接判断可清理性并显式标注；
6. **入口统一**：每个模块只有一个对外入口，模块间只通过彼此入口交互；
7. **模块自带 README**：记录约定、输入输出、依赖、产物与清理级别、使用示例。

开发前逐条自检；初始化已有项目时只记录偏差，不强制重构。

## 5. 一次性代码考古的分类规则

首次接触已有项目可以考古，但不得把代码中的注释、禁用分支或临时实现直接认定为“用户否决”。按证据分类：

| 发现 | 写入位置 | 要求 |
|---|---|---|
| 当前仍有效的明确用户规范或否决 | `RULES` / `DECISIONS` | 必须有用户原话或既有明确记录 |
| 文件中的临时实现、回退逻辑、隐藏约束 | `FILES` 的 S 字段 | 写清触发条件和影响 |
| 可复现故障、环境坑及解法 | `LESSONS` | 只记结论和验证方法 |
| 历史演进与重大决策背景 | `GitHistory.md` | 标日期和证据来源 |
| 用户明确说未来恢复或开发的方向 | `FUTURE` | 记录预留接口和来源 |
| 模型根据代码推测的历史意图 | `PREVIEW` 的疑问区或不写入 | 标“推断、待确认”，不得伪装成用户决定 |

考古完成后形成基线；后续会话只处理增量，不重复全量考古。

## 6. 旧版结构升级

已有 `AI_proj_note/rule.md`，但缺少字典或锚点时，执行一次迁移，不重新考古：

1. 阅读现有笔记和 [templates.md](templates.md)，创建 `index.md`，为现有内容补齐对应锚点；
2. 保留有效规范、否决、运维记录和各文件事实，只调整位置与格式，不借升级重写项目认知；
3. 将 rule.md 中的 Git History 完整移动到 `GitHistory.md`，按 commit hash 去重；能确认时间的按新到旧排列，无法关联 hash 的旧条目保留原相对顺序并标注“旧版迁移”；
4. 将 rule.md 中已完成的修改要求移入 `PROGRESS`，失效决策移入 `DECISION_ARCHIVE`；
5. 创建或修复 `CURRENT`。迁移默认以当前 HEAD 同时作为 `last_change_commit` 和 `last_history_commit` 基线，避免把旧提交再次补写；用户明确要求补记时另按主 SKILL 处理；
6. 验证所有旧内容都有去向、rule 不再含动态历史、字典与锚点一致，再提交结构升级。

## 7. 初始化验收

- 九个常驻文件存在，GitHistory 在首次记录历史或归档决策前创建；
- `index.md` 中九个常驻文件的目标路径和锚点真实存在且唯一；GitHistory 的三个锚点在创建该文件时一并验证；
- `rule.md` 没有 Git History、任务日志或大段考古叙述；
- `CURRENT` 含任务状态、`last_change_commit`、`last_history_commit`；
- 所有日志锚点明确，新到旧顺序不依赖额外说明；
- 所有推断已标注，所有用户决策有来源；
- `.gitignore` 与实际待提交文件通过安全检查。
