# 项目内外复用检索与通用组件设计

> 仅在命中主 SKILL 的复用双闸门时阅读。目标是优先复用或改造经过验证的资产，不以“自己写更快”为默认理由重复造轮子，也不为简单需求盲目引入重型依赖。

## 1. 先检索项目内资产

1. 读取 `REUSE`、`UI_REUSE`、相关 `BLOCKS` 与 `FILES`；
2. 用能力、输入输出、交互语义和中英文同义词搜索源码与依赖清单，例如“日期选择 / date picker / calendar”，不要只搜预想的组件名；
3. 检查候选资产的接口、扩展点、使用方、测试和限制，确认能否直接调用、配置或薄包装；
4. 若准备复制现有实现，先停下来判断应参数化、抽取共享能力还是统一迁移调用方。

## 2. 再联网检索外部成熟方案

常见通用能力和 UI/UX 组件必须实际检索，不得仅凭模型记忆断言“没有合适库”。高度项目定制的业务逻辑可记录“外部库不适用”及具体原因。

### 查询与来源

- 组合查询词：`技术栈 + 能力 + component/library`、`需求 + framework + accessibility`；必要时分别使用中英文；
- 使用可用的网页搜索、浏览器或包仓库工具，阅读**官方文档、官方仓库和包仓库页面**；聚合文章只用于发现候选，不能作为版本和 API 的最终依据；
- 可从官方生态页、框架官方文档的组件/集成导航和包仓库分类发现候选，再通过官方链接交叉核实；
- 记录候选名称、官方 URL、当前版本和关键结论。无可用联网工具时明确报告证据缺口，不假装已检索。

### 评估候选

按需求选择检查项，不要求为简单工具写冗长报告：

| 维度 | 核实内容 |
|---|---|
| 适配 | 框架、语言、运行时和渲染模式是否兼容 |
| 能力 | 是否覆盖当前真实需求，主题、配置、插槽或适配层能否支撑差异 |
| 维护 | 最近发布与提交、未处理问题、弃用或安全公告 |
| 合规 | 包身份与官方仓库一致，许可证满足项目分发方式 |
| 质量 | 测试、文档、TypeScript 类型等按场景判断 |
| UI/UX | 键盘操作、焦点管理、屏幕阅读器、移动端、边界与加载状态 |
| 成本 | 包体积、传递依赖、样式接入、数据迁移、学习及升级成本 |

不因 star 数单独做决定，不复制来历不明的源码，不安装无法确认官方归属的相似包名。

## 3. 做最小复用决策

候选和证据足以比较后选择：

- **A**：直接复用项目内资产；
- **B**：直接采用外部成熟库；
- **C**：参数化、包装或改造内部资产/外部库；
- **D**：从两处以上真实实现抽取共享能力；
- **E**：完全自研。

通常优先顺序为 A/B/C，再考虑 D/E；但应以实际适配与总成本为准，不机械选择依赖最多的方案。复杂交互和通用 UI 若选 E，必须证明成熟候选为什么不适用，不能只说“更灵活”或“自己写差不多”。

最小决策记录：

```text
需求与公共契约：
项目内候选：
外部候选（官方 URL、版本）：
选择（A/B/C/D/E）与理由：
稳定核心：
变化点与扩展点：
自研时 A–D 不适用的原因：
```

轻量决策放本轮计划；新模块或通用组件同步到 `BLOCKS` 与模块 README。不要因为记录决策而新建另一套笔记。

## 4. 采用、包装与自研边界

- 用项目包管理器安装，核实包名并锁定版本；遵循项目现有依赖与目录约定；
- 优先使用公开 API、配置、主题 token、插槽和事件，不直接修改第三方包内部源码；
- 项目需要统一交互或替换自由度时，在适配层封装外部库，业务代码依赖项目公共契约而非散落调用第三方 API；
- 包装层只暴露当前真实需求，保留必要的第三方类型、错误与事件语义，不无差别转发全部 API；
- 通用组件区分稳定核心和变化点，明确输入、输出、错误、扩展点及不适用场景；
- 抽象必须由至少一个当前需求或 `FUTURE` 中明确需求支撑，不为假想场景堆参数、插件体系或继承层级。

## 5. 编码后审计

1. 搜索相似实现，确认没有遗留“旧版 + 新版”并存，或明确记录暂存原因；
2. 应迁移的调用方已迁移，公共契约、错误行为和扩展点有一致定义与测试；
3. 外部依赖版本、许可证和关键接入约束写入适当项目文档；
4. 新内部资产、外部包与包装层按唯一键登记到 `REUSE` 或 `UI_REUSE`，包含能力关键词、官方来源、适用边界和使用方；
5. 复查 diff，确认没有为了“通用”引入无关抽象或重复实现。
