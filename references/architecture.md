# 新项目架构与核心技术设计

> 仅在新项目、重大架构调整或核心/高风险技术设计时阅读。只完成本轮所需决策，不一次性设计所有细节，不为假想需求增加抽象。

## 1. 最小架构基线

先依据用户需求和现有事实回答；未知内容标“待确认”，不以模型偏好替代产品决策。

1. **系统边界**：负责与不负责什么，用户和外部系统有哪些；
2. **功能域与模块**：按业务能力切分，明确公共基础设施与项目专用逻辑；
3. **依赖方向**：谁可以依赖谁，禁止哪些反向或循环依赖，模块只通过公共入口交互；
4. **数据事实源**：核心数据由谁创建、修改、持久化，缓存和产物不得冒充事实源；
5. **质量约束**：只记录会影响设计的性能、安全、隐私、可用性和成本要求，可量化时给出指标；
6. **运行与部署**：进程、任务、外部服务、存储及配套运维如何组合；
7. **演进条件**：关键方案在什么可观察条件下需要重新评估。

当前有效基线写入 `ARCHITECTURE`；候选方案、选择理由和否决原因写入 `DECISIONS`。目录结构只是结果，不能替代上述边界与流向。

## 2. 模块与复用规划

在候选模块层面区分：

- 通用基础设施、跨业务共享能力、项目专用业务逻辑；
- 直接复用、参数化/包装改造、从真实重复实现中抽取、完全自研；
- 当前使用方、明确后续使用方、稳定核心和变化点。

复用可能性用于确定检索范围，不代表所有模块都要通用化。项目内外候选检索和 A–E 决策遵循主 SKILL 的复用流程。

## 3. 核心数据结构

只针对核心数据记录：

- 访问模式：按键查询、顺序遍历、去重、范围查询、频繁增删等；
- 预期规模、增长方式、并发与持久化要求；
- 选型及理由，不用“常用”“更快”代替依据；
- 不变量：唯一性、引用关系、排序、删除与一致性规则；
- 序列化、迁移、备份和清理要求。

先保证事实源和不变量正确，再选择容器、索引或存储结构。访问模式或规模显著变化时重新评估。

## 4. 关键算法

仅对正确性、性能或资源消耗敏感的算法记录：

- 输入、输出、边界条件和精度要求；
- 预期数据规模及时间/空间复杂度；
- 标准库或成熟实现能否满足；
- 选择理由、替代方案和重新评估条件。

优先采用经过验证的标准实现和简单正确的算法。性能优化必须有基准或测量依据；加密、解析、压缩、排序等成熟领域不默认自研。

## 5. 公共契约与状态

模块间先约定输入输出、字段单位、默认值、错误类型、失败语义，以及按需涉及的幂等、超时、重试和兼容策略。

状态较多的流程明确合法状态、触发事件、非法转换、中断恢复和重复执行语义，避免规则散落为不可验证的分支。

## 6. 验收与风险验证

- 为核心路径给出至少一个正常案例和一个关键失败案例；
- 覆盖空输入、重复输入、外部失败和部分失败等本轮真实风险；
- 对不确定的库、算法、兼容性或性能假设，先做最小可丢弃实验，再让其他模块依赖该方案；
- 优先实现最薄垂直切片：入口 → 核心业务 → 数据或外部服务 → 输出 → 测试与运行验证。

垂直切片用于验证架构，不要求预先搭齐所有基础设施。

## 7. 完成前检查

- 实现是否符合依赖方向、数据事实源和公共契约；
- 是否出现重复实现、循环依赖或未经验证的核心假设；
- 数据不变量与关键异常路径是否有测试；
- 当前架构与决策是否仍符合实际实现，漂移是否已局部更新；
- 是否引入了没有当前或明确未来需求支撑的抽象。
