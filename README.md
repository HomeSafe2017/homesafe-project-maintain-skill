# Project Maintain Skill（AI 项目笔记管理）

一个面向 AI Agent（Claude Code、Cursor、Codex、Trae 等）的 **Skill**：指导模型在长期开发中为项目建立并持续维护一套 `AI_proj_note/` 认知资产，让**换人、换 Agent、换对话时，项目认知不丢**。

> 灵感来源：[AOCI-CODE](https://github.com/aoci-spec/aoci-code) 的"认知是可版本化资产"思想 —— Git 管理代码版本，本 Skill 管理项目认知。

## 解决什么问题

AI 长期开发一个项目时的典型痛点：

- 新会话 / 上下文压缩后，Agent 对项目"失忆"，每次重新摸索；
- 用户口头澄清的规范、否决过的方案，随对话蒸发，同样的坑反复踩；
- 换一个 Agent 接手，没有任何正式的认知交接物。

本 Skill 把"项目认知"变成**随仓库保存的笔记资产**：老 Agent 边开发边写笔记，新 Agent 由 Skill 指导读笔记接手，笔记就是两代 Agent 之间唯一的正式认知交接物。

## 核心设计

### `AI_proj_note/` 目录（七个文件）

| 文件 | 职责 | 更新时机 |
| --- | --- | --- |
| `rule.md` | 开发规范、否决记录（短路代码）、修改要求台账、Git History（最高优先级） | 规范变化立即追加；每次 git 提交后 |
| `files.md` | 文件级认知地图，一行式 FRAS 条目（职责/强关系/接口/隐藏约束） | 关键文件增删或语义变化 |
| `blocks.md` | 模块级认知地图：职责、依赖、约束、涉及文件清单 | 模块增删或依赖变化 |
| `vision_prefer.md` | 产品 UI 与用户偏好（UI/UX 审美、技术栈、沟通偏好） | 用户表达偏好时立即记录 |
| `preview.md` | 模型对产品的自主分析（定位/需求/场景/人群），唯一允许自由发挥的文件 | 认知深化或被用户纠正时 |
| `progress.md` | 任务进展日志，跨会话续接工作 | 每次任务完成或中断 |
| `lessons.md` | 踩坑记录：现象、根因、解法、教训 | 踩坑解决后 |

### 内置的默认开发规范

1. **注释规范**：代码各部分写清功能注释，注释含可全局搜索定位的 keyword；
2. **开发前模块规划**：动手前先明确模块划分、输入输出、测试方式，写入 blocks.md；
3. **Git 纪律**：每轮开发必须 git 提交，并在 rule.md 追加 Git History（提示词摘要 / 上版本用户评价 / 已实现功能）。

### 模块切割方法论（7 条）

核心检验标准：**不了解项目代码的人，仅凭目录结构、模块名和说明就能说出每个部分是做什么的。**

按功能域切顶层模块、相似模块聚成包、共用与特殊分离、通用基础设施单独成模块、数据目录可清理性一目了然、入口统一、模块自带说明。

### Agent 工作流

- **维护中的 Agent**：上下文 = skill + 已读笔记 + 对话，边开发边维护笔记；
- **新接手的 Agent**：上下文只有 skill + 对话，Skill 指导它按序读笔记 → 核对代码（以代码为准，防漂移）→ 接续维护；
- **回写纪律**：用户口头澄清、纠正的信息必须当场回写笔记 —— 对话是易失的，笔记才是资产。

## 使用方法

将 `project-develop.md` 作为 Skill / 系统提示词 / 项目规则安装到你使用的 AI 开发工具中（如 Trae 的 Skills、Claude Code 的 project instructions、Cursor 的 Rules）。首次接触项目时，Agent 会自动创建 `AI_proj_note/` 并开始维护。
